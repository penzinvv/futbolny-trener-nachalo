# Библия создания игры «Футбольный тренер. Начало»
Версия 1.0 · рабочий документ · 28 октября 2026

## 1. Назначение
Это библия **процесса разработки**, а не замена игровой библии с правилами футбольного менеджера. Здесь закреплено, как мы вместе создаём проект, распределяем работу, используем GitHub и Netlify, подключаем графику и принимаем решения.

## 2. Наш рабочий договор
- Ассистент самостоятельно делает всё, что может выполнить через доступные инструменты и подключённые плагины: проверяет репозиторий, редактирует код, создаёт файлы, проверяет структуру и готовит обновления.
- Пользователь загружает визуальные материалы в GitHub в папку `images/` (или в согласованную подпапку). Ассистент заранее говорит, какие материалы нужны, в каком количестве, формате, размере и с каким точным именем.
- Не просить пользователя проверять код вручную, если ассистент может сам прочитать файлы через доступные инструменты.
- Не заявлять, что изменение опубликовано или проверено в браузере, пока это не подтверждено.
- Сначала согласовывать игровые решения и отличать утверждённое от предварительного. Не выдавать рабочие гипотезы за утверждённые правила.
- Работать итерациями: небольшое изменение → сохранить в GitHub → проверить → сообщить, что сделано и что требуется от пользователя.
- Если действие невозможно выполнить через инструменты, честно объяснить ограничение и дать пользователю короткую пошаговую инструкцию только для необходимого действия.

## 3. Роли и ответственность
### Ассистент
- Проверяет текущий код и структуру репозитория перед редактированием.
- Вносит изменения в код и документы напрямую через GitHub-инструменты, если они доступны.
- Не удаляет пользовательские материалы и не переименовывает ассеты без необходимости.
- Готовит инструкции по визуальным материалам и проверяет, совпадают ли имена файлов в коде с реальными путями.
- Разделяет состояние GitHub и состояние опубликованного сайта: коммит не означает, что Netlify уже обновлён.
- Сообщает о тестах, которые реально проведены, и о тех, которые пока не проведены.

### Пользователь
- Создаёт и загружает графические и звуковые материалы.
- Если ассистент дал список материалов, загружает их в указанные пути и с указанными именами.
- По запросу проверяет сайт после публикации и сообщает результат или присылает скриншот.
- Не обязан самостоятельно редактировать код.

## 5. Правило для изображений и аудио
Пользователь загружает материалы в GitHub; ассистент подключает их в коде. Основная папка — `images/`.

Рекомендуемая структура:
- `images/avatars/players/` — портреты футболистов;
- `images/avatars/coaches/` — аватары тренера, если пользователь согласует отдельный каталог;
- `images/team-logos/` — эмблемы команд;
- `images/backgrounds/` — фоновые изображения и текстуры;
- `images/ui/` — значки, декоративные вставки, иллюстрации интерфейса;
- `music/` — фоновые музыкальные дорожки.

Это рекомендуемая организация; уже существующие пути не менять автоматически. Для каждого нового набора ассетов ассистент сообщает точные имена файлов, формат, нужный размер/соотношение сторон, количество и путь загрузки.

Предпочтительные форматы:
- фото и сложные фоны: JPG/WebP;
- прозрачные логотипы, значки и вырезанные портреты: PNG/WebP с прозрачностью;
- простые значки интерфейса: SVG, если источник безопасен и поддерживается;
- музыка: MP3 или OGG.

Правила подключения:
1. Сначала проверить фактические имена файлов в репозитории.
2. Использовать реальные пути и регистр символов без угадывания.
3. Для отсутствующего файла не делать вид, что изображение уже подключено; сообщить, чего не хватает.
4. Изображения должны масштабироваться адаптивно, не растягиваться и иметь разумный fallback.
5. Проверять отображение на мобильном и настольном экране, если возможно.
6. Не генерировать новые изображения вместо пользовательских ассетов, если пользователь собирается загрузить собственные.

## 6. Известные текущие материалы
- Пользователь сообщил, что добавил папку с музыкой. В коде реализован музыкальный плеер: запуск/остановка кнопкой, случайный порядок треков и повторное перемешивание после полного цикла. В браузере автоматический запуск звука может требовать первого нажатия.
- В репозитории есть каталог `images/avatarteam/` с файлами `avatarteam1.jpg`–`avatarteam6.jpg` (по результатам предыдущей проверки).
- Добавлена логика выбора аватара при создании команды и смены аватара один раз за сезон.
- Важно: на последнем скриншоте опубликованного сайта выбор аватара не отображался. Это указывает на то, что опубликованная версия отстаёт от GitHub либо нужные изменения ещё не попали в deploy. После обновления необходимо проверить сайт. Не считать функцию окончательно проверенной до теста на опубликованном сайте.
- Пользователь подтвердил, что стартовый экран, сохранение имени, главное меню и включение/выключение музыки работают на открытом сайте. Эти проверки относятся к той версии, которую пользователь тестировал, и не доказывают, что более поздние изменения уже опубликованы.

## 7. Текущая архитектура прототипа
- `index.html` — стартовый экран и разметка интерфейса;
- `src/app.js` — состояние, сохранение в localStorage, навигация, обработчики интерфейса, музыка и аватар;
- `src/styles.css` — оформление и адаптивная вёрстка;
- данные профиля сохраняются локально в браузере; полноценный сервер, авторизация и облачная синхронизация пока не подтверждены;
- некоторые разделы являются заглушками до согласования механик (например, лига, воспитание, цели и полноценные тренировки);
- локальное сохранение браузера не равно аккаунту, который синхронизируется между устройствами.

## 8. Процесс работы над каждой функцией
1. Уточнить ожидаемое поведение, если есть существенная неоднозначность.
2. Проверить существующие файлы и актуальные пути в GitHub.
3. Разделить требования на согласованные, предварительные и открытые.
4. Внести минимально необходимое изменение, не ломая существующие функции.
5. Проверить синтаксис/структуру настолько, насколько позволяют инструменты.
6. Сохранить изменения в GitHub с понятным сообщением коммита.
7. Если нужно изображение/звук — сначала запросить у пользователя конкретные материалы с точными именами.
8. После публикации попросить проверить только те сценарии, которые невозможно подтвердить самостоятельно.
9. В ответе перечислить сделанное, ссылки на изменённые файлы, известные ограничения и следующий шаг.

## 9. Чек-лист для визуальных материалов
Перед запросом ассетов ассистент должен указать:
- зачем они нужны в игре;
- точную папку назначения;
- точные имена файлов и порядок нумерации;
- формат (JPG, PNG, WebP и т. п.);
- желательное разрешение или соотношение сторон;
- количество файлов;
- требования к прозрачности и единому стилю;
- нужно ли обновить код после загрузки (обычно да — это делает ассистент).

## 10. Правила тестирования
- Не считать коммит доказательством работающего сайта.
- Не считать статус deploy доказательством корректного поведения функции.
- После обновления проверять страницу в обычном и мобильном размере.
- Для сохранения данных проверять перезагрузку страницы; для ограничений по сезону — повторное действие в том же сезоне и сброс при смене сезона, когда сезонная система будет реализована.
- Для музыки проверять старт по кнопке, остановку, переход к следующему треку и обработку отсутствующего файла.
- Для ассетов проверять каждый путь и fallback.
- Не обещать автоматическую публикацию, если связь GitHub–Netlify не настроена.

## 12. Ближайшие шаги
1. Убедиться, что новые файлы аватаров и код выбора аватара попали в актуальный deploy Netlify.
2. Проверить стартовый экран на опубликованном сайте и проверить смену аватара.
3. Зафиксировать структуру папки `images/` и согласовать единые правила именования с уже загруженными файлами.
4. Ассистент составит очередной список нужных изображений/иконок/фонов, пользователь загрузит их, затем ассистент подключит их кодом.
5. Продолжить реализацию игровых систем по очереди, не выдавая заглушки за готовые механики.

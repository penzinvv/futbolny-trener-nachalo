## 1. Правило работы с проектом и публикации

Рабочий процесс, согласованный с владельцем проекта:

1. Проверить актуальный код и файлы в GitHub `main`.
2. Если изменения должны отражать состояние основного сайта, сначала получить от владельца актуальные файлы основного хостинга и сравнить их с GitHub. Нельзя считать GitHub автоматически равным основному хостингу.
3. Разрабатывать и проверять изменения в GitHub и на тестовом сайте Netlify.
4. Не изменять основной сайт `streetfootballstart.ru` напрямую и не выполнять на нём развёртывание от имени помощника.
5. Владелец проверяет тестовую версию. Только после его подтверждения он сам скачивает ZIP из GitHub и устанавливает согласованную версию на основной хостинг.
6. Не удалять сохранения, резервные копии, ветки, таблицы или данные пользователей без отдельного согласования.

**Важно:** автоматическая публикация GitHub → Netlify зависит от реальных настроек проекта Netlify. Её нельзя считать подтверждённой только по тексту документации. После изменений нужно отдельно проверить deploy status и поведение тестового сайта. ZIP с GitHub содержит состояние репозитория на момент скачивания и сам по себе не включает данные, которые хранятся в браузере или Supabase.

## 2. Технологическая структура

- Браузерная игра на HTML, CSS и JavaScript без обязательной регистрации для начала игры.
- `index.html` задаёт структуру интерфейса.
- `src/styles.css` содержит оформление и адаптивную раскладку.
- `src/app.js` содержит состояние игры, рендеринг страниц, правила, симуляцию матчей, тренировки, магазин, события и интеграцию с облачными функциями.
- `data/league.json` содержит исходные данные команд и футболистов.
- Изображения, музыка и другие игровые ресурсы загружаются из папок проекта.
- В клиентском коде используется Supabase JS при наличии библиотеки `window.supabase`. Для серверных действий используется Edge Function `career-api`.

## 3. Создание и состояние карьеры

### Реализовано в исходниках

- Первый запуск предлагает указать имя тренера и название команды.
- Можно выбрать аватар тренера и эмблему команды.
- Состояние игры хранится в объекте `state` и сериализуется в браузерный `localStorage` под ключом `football-coach-start-v1`.
- Состояние включает, в частности, имя тренера и команды, сезон и игровой день, опыт, валюту магазина, постоянный и сезонный рейтинги, уважение, игроков, отношения, результаты матчей, события, историю карьеры, данные магазина, назначения портретов и другие игровые поля.
- Изменения состояния вызывают сохранение в локальное хранилище; `saveState()` также запускает механизм сохранения облачного снимка.
- Предусмотрены резервные копии локальной карьеры перед отдельными операциями с аккаунтом и облачным восстановлением.

### Ограничения

- `localStorage` относится к конкретному браузеру и профилю устройства. Очистка данных браузера или переход на другое устройство сами по себе не переносят локальную карьеру.
- Нельзя считать облачное сохранение исправным только потому, что в коде есть вызовы Supabase: необходимы доступная конфигурация, действующая серверная функция, нужная схема БД и браузерный тест.
- Код игры и клиентское сохранение не являются защищённым от подмены серверным игровым состоянием.

## 4. Аккаунт и облачные данные

В интерфейсе есть аккаунт тренера с режимами входа, регистрации, выхода и восстановления пароля. Гостевой режим предусмотрен: начать играть можно без регистрации.

В клиентском коде присутствуют два связанных механизма:

- **Облачный снимок состояния карьеры:** отправка и получение состояния игры через серверный запрос, управление ревизией снимка, обработка конфликтов и создание резервных копий перед некоторыми операциями восстановления.
- **Структурированная карьера:** синхронизация тренера, команды и состава через действие `career-api`. Серверная функция проверяет токен Supabase Auth и ограничивает операции текущим пользователем.

В `career-api` присутствуют обработчики получения структурированной карьеры, начальной регистрации карьеры и сброса карьеры. Серверный сброс рассчитан на закрытие текущей команды и завершение активных записей истории, а не на удаление публичных рейтингов, сообщений чата или чужих данных.

**Не подтверждается одним только исходным кодом:** актуальность развёрнутой версии Edge Function, наличие всех необходимых таблиц и политик БД, успешная синхронизация на реальном аккаунте, восстановление на другом устройстве и согласованность структурированной карьеры с локальным снимком. Это требует отдельного теста на тестовом окружении.

## 5. Игровое время и сезоны

- Продолжительность таймера игрового дня задана константой `GAME_DAY_DURATION_MS = 60000` — 60 секунд.
- В интерфейсе предусмотрены запуск/пропуск дня, показ таймера и переход к следующему дню.
- Сезон рассчитан на 182 игровых дня.
- Для даты используются номер сезона и номер дня; календарь отображает дни сезона и запланированные матчи.
- В календаре предусмотрены дни матчей лиги, этапы кубка и отдельные товарищеские/межсезонные матчи.
- На смене сезона код начисляет сезонные бонусы рейтинга и карьерные награды, записывает некоторые итоговые поля, увеличивает номер сезона и возвращает игровой день к 1.

**Известное ограничение:** в проверенном коде нет полноценного автоматического повышения команды в верхнюю лигу или вылета в нижнюю по итогам места в таблице. Сама по себе победа в нижней лиге не переводит команду в верхнюю. Текущая лига команды берётся из её данных, а автоматический переход между лигами не реализован.

**Известное несоответствие истории сезона:** код при завершении сезона записывает набор полей, который не полностью совпадает с полями, которые читает интерфейс архива сезонов. Поэтому нельзя считать отображение полного архива сезона корректным без отдельного исправления и теста. Текущий профиль тренера рассчитывает статистику сезона по данным текущего сезона и не заменяет полноценный архив итогов всех сезонов.

## 6. Команды, состав и футболисты

- Метаданные лиги находятся в `data/league.json`; полный справочник футболистов из пользовательского документа — в `data/player-database.json`.
- В справочнике 210 футболистов с постоянными ID, четырьмя игровыми характеристиками, позицией, национальностью, портретом и исходным назначением: 12 стартовых команд (101 игрок), девять резервных команд (84 игрока) и «Свободный двор» (25 игроков).
- При создании новой карьеры составы 12 стартовых команд восстанавливаются по исходному документу, а не перемешиваются случайно. Возраст каждого игрока назначается случайно в диапазоне 14–20 лет один раз при создании карьеры и затем сохраняется.
- В репозитории доступны все 150 файлов портретов `images/portretplayers/portret1.jpg` — `portret150.jpg`; индекс портрета закреплён за записью игрока.
- Игроки имеют амплуа ВР, ЗЩ, ПЗ и НП, национальность, имя и набор профильных характеристик. Старые сохранения не должны автоматически пересобираться.
- Есть список состава, карточки игроков и профили футболистов.
- Есть система отношений тренера с игроками; данные отношений сохраняются в состоянии карьеры. Часть информации о футболисте раскрывается в зависимости от отношения.
- Есть данные физического состояния футболистов, влияние усталости на эффективную оценку в матче и восстановление состояния в игровые дни.
- Для отдельных событий предусмотрены временная недоступность футболиста и разрешение/отклонение запроса на отсутствие.

### Портреты

- Код использует изображения `images/portretplayers/portret1.jpg` — `portret150.jpg`.
- Для новых карьер `portraitIndex` берётся из `data/player-database.json`; назначение портретов не зависит от случайного распределения футболистов. Для совместимости старых сохранений сохраняется существующая очередь назначений.
- Отображение портрета использует сохранённый индекс игрока, а не должно выбирать новое изображение при каждом рендере.
- Если ресурс отсутствует или повреждён, фактическое поведение следует проверять отдельно; документ не обещает наличие всех 77 файлов в каждом развёртывании.

## 7. Лига и официальные матчи

### Лига и таблицы

- В коде предусмотрены «Нижняя лига» и «Верхняя лига».
- Для официальных туров задан календарь игровых дней.
- Симуляция фоновых результатов создаёт результаты матчей других команд в соответствующем туре.
- Таблица лиги строится по сохранённым результатам текущего сезона и учитывает сыгранные матчи, победы, ничьи, поражения, забитые и пропущенные мячи и очки.
- Сортировка таблицы использует очки, разницу мячей, забитые мячи и название команды.
- Результат учитывается в таблице только при соответствии ожидаемому туру, лиге и дню матча.

### Проведение матча

- Есть отдельный экран официального матча, поле, составы, тактические схемы, события и экран итогов.
- Для NPC предусмотрен выбор схемы и стартового состава по оценкам футболистов.
- Код рассчитывает игровые события и статистику матча, рейтинги футболистов и изменения характеристик по итогам матча.
- Есть замены, карточки, голы, травмы/недоступность и усталость в рамках реализованных правил симуляции.
- Состояние незавершённого матча сохраняется в карьере; код содержит попытку возобновить сохранённую автосимуляцию после загрузки.
- После официального матча результат добавляется в `state.leagueResults`, сохраняется краткая запись в истории официальных матчей, обновляются рейтинг и уважение, публикуется игровое событие.

### Ограничения

- Результаты и таблицы хранятся в состоянии браузерной карьеры, если отдельная серверная система не используется специально; это не централизованная серверная база официальных результатов.
- Автоматические переходы между лигами по итогам сезона не реализованы.
- Правильность матча, его возобновления, таблиц и сохранения после перезагрузки нужно проверять браузерными сценариями. Наличие соответствующих функций в коде не является таким тестом.

## 8. Кубок «Достаток» и календарные матчи

В коде предусмотрены даты четвертьфиналов, полуфиналов, финала кубка и отдельных товарищеских матчей. Есть построение пар, симуляция кубковых матчей, отображение сетки/страницы кубка и добавление карьерных наград по итогам сезона.

Это локальная игровая симуляция. Наличие интерфейса кубка не означает, что все возможные ветки сетки, повторный вход в матч и все сезонные случаи были протестированы.

## 9. Тренировки и мини-игры

В коде присутствует раздел тренировок и логика нескольких мини-игр, в том числе:

- «Три в ряд»;
- мини-игра вратаря с ловлей мячей;
- мини-игра защитника с реакцией на появляющиеся мячи;
- «Змейка» с мячом;
- индивидуальные тренировки и командная тренировка;
- кулдауны отдельных действий и обработка результата.

Код содержит начисление опыта тренера, отдельного баланса магазина и изменений отношений/характеристик в зависимости от конкретного действия. Опыт тренера и валюта магазина представлены отдельными полями; функция начисления опыта может пополнять оба баланса, а покупка списывает валюту магазина.

**Важно:** награды, кулдауны и прогресс хранятся на стороне клиента и не являются авторитетными серверными значениями. Точные суммы наград должны проверяться по актуальной реализации конкретной мини-игры, а не переноситься из старых записей документации. До отдельного теста нельзя гарантировать отсутствие ошибок при повторном открытии мини-игры, смене страницы или перезагрузке.

## 10. Игровые события и почта тренера

- В состоянии предусмотрены лента игровых событий и хроника тренера.
- Код публикует события по ключу, чтобы некоторые повторяющиеся события не создавались повторно.
- Предусмотрена выдача запланированных сообщений/событий по игровым дням.
- Есть запросы футболистов об отсутствии, действия тренера по таким запросам и связанные последствия для опыта, отношений и временной доступности игрока.
- События могут открываться во всплывающем окне и отображаться в хронике.

Даты, условия и награды каждого отдельного события определяются текущими массивами и функциями в `src/app.js`. Старые тексты о запланированных письмах не считаются действующими, если соответствующего правила нет в актуальном коде.

## 11. Трансферы и скаутские события

- Код содержит логику профессионального ухода футболиста при определённых скаутских условиях и обработку ожидающих уходов.
- Есть система временной недоступности футболистов.
- Для NPC-команд предусмотрена случайная вероятность обмена игроками между командами; этот код ограничен условиями версии правил карьеры и наличием начального распределения состава.
- Есть игровые разделы трансферов/свободного двора, однако доступность конкретного действия и его полный цикл нужно сверять с текущим обработчиком страницы и данными.

**Не следует считать реализованным**, если нет соответствующего кода: автоматическое повышение/понижение команды по таблице, полноценный защищённый серверный трансферный рынок или синхронизация всех перемещений игроков между независимыми клиентами.

## 12. Кабинет тренера, рейтинг и награды

- Есть кабинет тренера и профиль тренера, где отображаются доступные текущие показатели и статистика.
- В состоянии существуют XP, постоянный рейтинг, сезонный рейтинг и уважение — это разные показатели.
- Код содержит начисление очков постоянного и сезонного рейтинга, журнал начислений и сезонные бонусы.
- По итогам матчей и сезона могут формироваться карьерные награды; есть отображение полки наград и бейджей экипированных званий.
- Профиль тренера рассчитывает статистику по результатам, доступным для текущей команды/сезона.

**Ограничение:** код не обеспечивает автоматически корректный полный архив каждого сезона. Исторические данные профиля и архивные карточки следует считать надёжными только после согласования полей записи и отображения и отдельного теста.

## 13. Онлайн-рейтинг и онлайн-рекорды

### Онлайн-рейтинг тренеров

- Интерфейс отправляет единый результат с двумя показателями: **опыт аккаунта (XP)** и **постоянный рейтинг**.
- В отправляемый снимок также входят данные отображения тренера и команды, включая аватар/эмблему и экипированные звания, а также некоторые метаданные и награды.
- Загрузка и отправка выполняются через клиентские запросы к серверному API. При ошибке интерфейс должен показать сообщение об ошибке.

### Онлайн-рекорды

- В коде предусмотрены отдельная страница онлайн-рекордов и отправка кандидатов рекордов.
- Серверная функция `career-api` содержит действия чтения/отправки онлайн-результатов; клиент ограничивает и валидирует часть передаваемых полей.
- Наличие логики топа-100 в коде не доказывает, что все категории заполнены, серверная схема актуальна или что предельная вместимость была протестирована.

**Требуется отдельная проверка:** доступность Edge Function, схемы БД и миграций, загрузка таблиц, конкурентные отправки, сохранение снимков и отображение на тестовом сайте.

## 14. Магазин и внешний вид

- В коде есть каталог предметов магазина, цены и редкости, включая аватары, логотипы и звания тренера/команды.
- При покупке проверяются корректность предмета, цена, повторная покупка и достаточность баланса.
- Купленные предметы сохраняются в состоянии; экипированные предметы записываются по слотам.
- Отображаемый аватар и логотип могут браться из экипированного предмета магазина либо из базового выбора.
- Экипированные звания отображаются в интерфейсе как бейджи.
- Магазин использует изображения из ресурсов проекта; визуальные эффекты, анимации и наличие всех файлов следует проверять на тестовом сайте.

## 15. Музыка, фон и интерфейс

- В шапке интерфейса предусмотрено управление музыкой, а код загружает список файлов из папки `music` с резервным списком имён треков.

## 16. Сброс карьеры

- В интерфейсе разработчика есть действие «Начать карьеру с нуля» с подтверждением.
- Клиент обращается к серверному действию `reset-career` и удаляет локальное состояние только после подтверждения сервером.
- Код сброса отдельно оговаривает, что публичные рейтинги, чат и данные других пользователей не должны удаляться.
- Сброс необратим для текущего прогресса, поэтому перед его выполнением необходимо внимательно читать подтверждение и не запускать его для диагностики без разрешения владельца.

## 19. Главные известные пробелы по текущему коду

1. **Повышение и понижение между лигами:** не реализовано в проверенном коде.
2. **Архив сезонов:** запись итогов и чтение архива используют несовпадающие поля; требуется согласование и тест.
3. **Серверная авторитетность:** основная симуляция и значительная часть игрового состояния выполняются на клиенте.

5. **Публикация:** статус тестового Netlify и соответствие основного домена GitHub нужно проверять фактически, а не выводить из старых записей.

Этот документ намеренно не содержит старого журнала версий и неподтверждённых планов. Новые изменения следует добавлять в соответствующие актуальные разделы только после проверки исходников; историю релизов при необходимости вести отдельно.
